## 三、遇到的问题及解决方法

### 问题一：Service 层架构重构的平滑过渡

**现象**：项目初期部分业务逻辑直接写在 Controller 中，随着功能增加 Controller 越来越臃肿，且业务逻辑无法被其他模块复用。

**解决**：逐步将 Controller 中的业务逻辑提取到独立的 Service 接口和实现类中。Controller 只负责参数接收和返回封装，Service 负责核心业务逻辑，Mapper 负责数据访问。重构过程中保持接口签名不变，确保前端调用不受影响。

**效果**：代码结构清晰，各层职责明确，后续新增功能可以直接复用已有的 Service 方法。

### 问题二：硬编码用户 ID 的全局替换

**现象**：项目初期使用固定用户 ID（如 `sellerId = 1001L`、`buyerId = 1002L`）进行开发和测试，但上线联调时需要根据登录用户动态获取。

**解决**：通过 `TokenInterceptor` 在请求处理前从 Redis 中解析 Token 获取当前用户 ID，存入 `request.setAttribute("currentUserId")`。在 Controller 和 Service 中统一从 request 属性获取用户 ID，替换所有硬编码值。逐个接口排查确保无遗漏。

**效果**：每个登录用户的操作都能正确关联到自己的身份，不会出现"A 用户的操作被记录到 B 用户名下"的问题。

### 问题三：WebSocket 认证与 HTTP 认证的统一

**现象**：HTTP 接口通过请求头的 `Authorization` 字段携带 Token 进行认证，但 WebSocket 握手时浏览器不支持自定义请求头。

**解决**：WebSocket 连接时通过 URL 查询参数携带 Token（`ws://localhost:8080/ws/chat?token=xxx`），`ChatWebSocketHandler` 在连接建立前从查询参数中解析 Token 并通过 Redis 验证。验证失败则拒绝连接。

**效果**：WebSocket 和 HTTP 两种通信方式使用同一套 Token 认证体系，保证了认证的一致性和安全性。

### 问题四：订单状态机的并发一致性

**现象**：用户快速连续点击"取消订单"和"确认收货"按钮时，可能出现状态冲突。

**解决**：在 Service 层增加状态前置校验——操作前先检查订单当前状态是否允许该操作。例如只有"已支付"状态的订单才能取消或确认收货，已取消的订单不能再进行任何操作。

**效果**：杜绝了订单状态的非法流转，保证了数据一致性。

### 问题五：单元测试中的数据隔离与 Mock 策略

**现象**：单元测试需要隔离测试环境，避免对真实数据库产生影响，同时需要 Mock 外部依赖（如 Redis、微信 API）。

**解决**：使用 Mockito 框架 Mock Mapper 层和外部服务依赖，使用 `@ExtendWith(MockitoExtension.class)` 进行纯单元测试。每个测试方法独立设置 Mock 行为，保证测试之间互不影响。

**效果**：12 个测试文件全部通过，可以在不启动外部服务的情况下快速验证业务逻辑正确性。

## 四、总结与展望

### 4.1 总结

通过本次项目实践，我在后端业务开发和软件质量保障方面收获良多：

**技术层面**：深入掌握了 Spring Boot 的三层架构（Controller → Service → Mapper）设计模式，学会了 WebSocket 实时通信的服务器端实现（连接管理、消息路由、持久化存储），了解了 Token 认证在 HTTP 和 WebSocket 两种协议下的统一方案。从编写单个 API 到负责 8 个业务模块，逐步建立了后端业务的全局视角。

**工程层面**：Service 层重构的经历让我认识到代码架构的重要性——好的架构不是一开始就设计出来的，而是在业务增长过程中逐步演进出来的。关键是在每次重构时保持对外的接口稳定。

**质量层面**：单元测试不是为了交作业而写的，而是为了保证系统在频繁改动后仍然正确的保障。通过编写 12 个测试类，我学会了如何设计有效的测试用例、如何使用 Mock 隔离依赖、如何在回归测试中快速定位问题。

### 4.2 展望

- 订单状态机可以引入更完善的事件驱动模型，支持更多中间状态
- 聊天系统可以增加群聊、图片消息等功能
- 补充更多边界条件测试和异常场景测试
- 引入代码质量工具（如 SonarQube）进行静态分析

## 五、对课程的建议

1. 建议课程明确代码规范要求（如必须使用 Service 层、禁止 Controller 中写业务逻辑），并在中期进行代码审查，避免后期重构成本过高
2. 单元测试的建议早点引入——不是等项目写完再补测试，而是在开发功能的同时写测试
3. 建议在项目中引入 Git 分支管理，每位成员在自己的分支上开发，通过 PR 合并，这样既能追踪每个人的贡献，也培养了工程化协作习惯
