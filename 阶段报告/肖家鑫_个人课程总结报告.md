# 肖家鑫 个人课程总结报告

## 一、本人在本综合项目实践中承担的工作

在本项目中，我担任**组长**兼**后端架构师**，同时独立完成了前端 Web 端全栈开发。我的工作可以分为以下七个方面：

### 1.1 后端架构与基础设施

- 搭建 Spring Boot 3.2.3 项目脚手架，集成 MyBatis-Plus 3.5.5、Redis、WebSocket 等核心组件
- 设计并维护统一返回结构 `Result<T>`（code/msg/data），所有接口返回值格式统一
- 实现全局异常处理机制，将业务异常和系统异常统一捕获并返回规范格式
- 编写 `CorsConfig.java` 解决前后端分离开发中的跨域问题
- 编写 `MybatisPlusConfig.java` 配置分页插件，修复分页查询不生效的问题
- 编写 `WebMvcConfig.java` 配置静态资源映射和拦截器注册
- 编写 `TokenInterceptor.java` 实现统一鉴权体系，采用白名单策略区分匿名接口和需登录接口，Token 存入 Redis 管理登录态
- 编写 `SecurityConfig.java` 配置 BCrypt 密码加密器
- 编写 `OpenApiConfig.java` 接入 SpringDoc/Swagger，实现接口文档自动化生成
- 编写 `DataInitializer.java` 实现启动时数据检查与初始化
- 统一管理环境变量（微信 AppID/Secret、腾讯地图 Key、DeepSeek API Key、数据库、Redis），避免敏感信息硬编码

### 1.2 数据库设计

- 从零设计全部 11 张数据库表，随项目阶段逐步扩展：
  - 第一阶段：`sys_user`（用户）、`biz_product`（商品）、`biz_order`（订单）
  - 第二阶段：扩展用户角色字段、商品图片字段，新增 `biz_chat_session`（聊天会话）、`biz_chat_message`（聊天消息）
  - 第三阶段：新增 `biz_category`（分类）、`biz_favorite`（收藏）、`biz_product_comment`（商品评论）、`biz_order_review`（订单评价）、`biz_student_roster`（学籍名册）、`biz_user_behavior`（用户行为）
- 编写 `database.sql` 完整建库建表脚本，包含索引设计
- 编写演示数据生成脚本 `tools/generate_demo_data.py`，产出了包含 320 个用户、3000 件商品、1200 笔订单的中文校园场景验收数据集（`data.sql`）

### 1.3 核心业务功能

- **Redis Lua 原子库存预扣**：针对高并发抢购场景下的库存超卖问题，编写 Lua 脚本将"查询库存"和"扣减库存"封装为一条原子指令在 Redis 中执行，并实现缓存击穿时的双重检查锁定回填机制
- **认证体系演进**：从第一阶段的模拟 Token，到第二阶段的数据库 + Redis Token 方案，再到第三阶段的微信小程序 code2Session 真实登录，全程把控认证方案的设计与实现
- **微信小程序登录**：完整接入微信官方登录流程（uni.login → code2Session → openid → Redis Token），编写 `WechatAuthService` 和 `WechatProperties` 配置类
- **腾讯地图面交点**：接入腾讯地图 WebService API，实现地点搜索和逆地址解析功能，并为校园场景设计了常用面交点兜底列表，编写 `TencentMapService`、`TencentMapProperties` 和 `LocationController`
- **学号实名校验**：编写 `StudentVerificationService`，基于本地学籍名册 `biz_student_roster` 实现学生身份校验，作为发布商品的实名门禁，并在设计文档中明确标注"模拟但可替换"的边界
- **文件上传**：编写 `FileController.java`，实现图片上传功能，包含多层安全校验（文件大小 10MB 限制、MIME 类型白名单、扩展名白名单、UUID 重命名防冲突、路径遍历防护）

### 1.4 AI 智能推荐系统

独立设计并实现两套推荐系统：

- **DeepSeek LLM 智能找货**（`AiRecommendService` + `DeepSeekProperties`）：
  - 设计系统提示词，让 DeepSeek 从用户自然语言描述中提取关键词、分类和价格上限，并以 JSON 格式结构化返回
  - 实现 3 个 API 端点：`/api/ai/recommend`（描述驱动商品搜索）、`/api/ai/chat`（对话式商品推荐 + 商品卡片嵌入回复）、`/api/ai/dialogue`（纯对话模式）
  - 设计三级回退策略：AI 解析 → 本地关键词拆分搜索 → 热门商品兜底，保证服务在任何情况下都有可用结果

- **基于行为的推荐引擎**（`RecommendationService`）：
  - 设计用户行为权重模型：购买行为 5 分、收藏 4 分、评论 3 分、浏览 1 分
  - 实现分类偏好分析 + 多因子商品评分公式（分类偏好 × 5 + 收藏数 × 4 + 评论数 × 2 + 浏览量）
  - 支持个性化排序推荐

## 三、遇到的问题及解决方法

### 问题一：高并发下库存超卖

**现象**：初始测试中，多用户同时抢购一件孤品商品时，数据库 `UPDATE` 语句在并发请求下存在行锁竞争，导致实际卖出数量超过库存。

**原因分析**：传统的"先查询库存 → 判断是否充足 → 扣减库存"流程在高并发下不是原子操作，多个请求同时读到库存为 1，都会判定充足并执行扣减。

**解决方案**：编写 Redis Lua 脚本，将"查询库存"和"扣减库存"两个步骤封装为一条原子指令在 Redis 服务端执行。针对缓存击穿场景（Redis 中无该商品库存缓存），实现双重检查锁定机制，从数据库加载真实库存并同步至 Redis 后重试。

**效果**：并发下单链路线程安全，课程演示环境中可稳定复现正常购买和库存不足两种场景。

### 问题二：Spring Boot 3.x 版本兼容性

**现象**：Spring Boot 3.x 弃用了 javax.* 命名空间，全面迁移到 Jakarta EE (jakarta.*)，导致部分依赖（如 Servlet API、Validation API）报找不到类的错误。

**解决方案**：查阅 Spring Boot 3.x 官方迁移指南，将全部依赖更新为兼容版本，手动调整代码中所有 `javax.*` 包引用为 `jakarta.*`，并同步更新 Maven 依赖版本号。

**效果**：后端稳定运行于 Java 17 + Spring Boot 3.2.3，未再出现兼容性问题。

### 问题三：前后端接口口径不一致

**现象**：联调初期，前端调用接口时频繁出现字段名不匹配的问题——后端返回 `msg` 但前端读取 `message`，后端返回 `data` 但前端期望直接拿到数组等。

**解决方案**：坚持以当前源码为准的原则，统一所有接口返回结构为 `{ code: 200, msg: "success", data: {} }`。与前端同学对齐关键字段命名规范（如 `sellerId`、`categoryId`、`createTime`），并在阶段报告中持续回写字段对照关系。

**效果**：减少联调摩擦，接口口径统一后前端开发效率明显提升。

### 问题四：真实第三方服务接入与可控性的平衡

**现象**：B 范围要求接入微信登录和腾讯地图，但微信 AppID/Secret 需要真实申请且审核周期长，学校官方实名接口暂不可用。

**解决方案**：区分能力边界——微信登录和腾讯地图按真实服务接入，通过环境变量管理密钥；学号实名校验使用本地 `biz_student_roster` 名册模拟学校权威数据源，验证逻辑完整，数据可替换。在设计文档和验证手册中明确标注每项能力属于"真实接入"还是"模拟但可替换"。

**效果**：既有真实的第三方服务集成体验，又保证在任何环境下都能稳定演示和验收。

### 问题五：功能增长后的回归与稳定性压力

**现象**：B 范围新增 8 项功能后，每次代码改动都可能影响多条已有链路（如修改商品状态可能影响首页、详情、订单、聊天等多个环节）。

**解决方案**：推动后端补充单元测试覆盖关键服务，编写 20 项完整验证手册，将验证流程拆分为可逐项检查的步骤（环境准备 → 数据库检查 → 后端测试 → 用户端主链路 → 管理端治理链路 → 证据留存）。

**效果**：全部测试通过，验证手册可按主链路逐项确认，保证了验收阶段系统的稳定性。

## 四、总结与展望

### 4.1 总结

通过本次综合项目实践，我在以下几个方面有了显著收获：

**技术层面**：完整经历了一个 Web 后端从零到交付的全栈开发周期。从 Spring Boot 脚手架搭建开始，逐步深入 Redis 并发控制、WebSocket 实时通信、DeepSeek AI 集成、微信和腾讯地图第三方 API 接入，再到独立开发一个完整的 Vue 3 前端应用。这不仅加深了我对各个技术栈的理解，也让我认识到不同技术组件之间如何协同工作。

**工程层面**：深刻认识到"能实现"与"能交付"之间的差距。一个功能不仅要代码写得通，还要有文档说得清、有测试验证过、有验收手册可复现。特别是第三方密钥管理、数据库初始化脚本、环境变量配置这些看似"边缘"的工作，实际上是系统可复现运行的基础。

**管理层面**：组长的职责不仅是完成个人开发任务，更要从整体交付的角度把控节奏。需要在技术深度（确保后端架构稳定可扩展）和项目广度（协调前后端接口、管理任务优先级和风险）之间找到平衡。推动团队从"各自开发功能"转向"以主链路闭环为目标协同推进"。

**质量层面**：文档、接口、页面和数据库结构必须同步演进。任何一方的滞后都会导致返工——接口改了但文档没改会导致联调出错，数据库加了字段但页面没接会导致数据丢失。验证闭环比功能数量更重要。

### 4.2 展望

当前系统已实现完整的交易闭环和课程验收所需的全部功能，后续可进一步扩展的方向包括：

- 将学号实名校验从本地名册升级为对接学校官方认证接口
- 接入微信支付实现真实线上交易
- 推荐系统从当前规则权重模型升级为协同过滤或向量召回
- 部署至云服务器并建立 CI/CD 流程
- 管理端适配移动端访问

## 五、对课程的建议

1. **关于项目启动阶段**：初期环境搭建和版本兼容性排查消耗了大量时间（如 Spring Boot 3.x Jakarta EE 迁移）。建议课程提供预配置的开发环境（Docker 镜像或虚拟机模板），让学生能更快进入业务实现阶段。

2. **关于第三方服务的时间窗口**：微信小程序和腾讯地图的开发者审核周期较长（通常 1-2 周）。建议课程在项目启动时就通知学生提前申请，避免到了需要联调时还在等待审核。

3. **关于验收标准的明确性**：建议在项目中期就给出验收清单模板，明确区分"能跑"和"可验收"的标准——不仅要求功能可演示，还要求关键路径有测试覆盖、有文档支撑、有可复现的启动和验证步骤。

4. **关于团队协作**：建议课程引入基础 Git 协作规范（如分支策略、代码评审流程），让学生提前接触工程化的团队协作方式。这比只关注个人代码量更能培养学生的工程素养。
