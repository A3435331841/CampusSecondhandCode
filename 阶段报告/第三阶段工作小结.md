# 基于 Uni-app 的校园二手交易平台 - 第三阶段工作小结

## 一、阶段概述

本阶段是在前期完成需求分析、系统设计、基础架构搭建以及核心交易链路初步联调的基础上，围绕“补齐 B 范围功能、提升系统完整度、形成可验收版本”的目标继续推进。相比前一阶段主要解决“系统能否跑通”的问题，本阶段更加关注真实接入、业务闭环、后台治理、测试验证和验收材料沉淀。

经过本阶段开发与联调，系统已经从“可演示 MVP”进一步完善为具备较完整课程验收条件的版本。用户端已经覆盖微信登录、学号实名、商品发布、图片上传、面交点选择、商品收藏、评论留言、即时聊天、下单收货、买卖双方评价和首页推荐等能力；管理端补齐了分类管理、商品审核、实名状态查看、评论治理和数据看板等功能；后端围绕认证、交易、互动、推荐、信用分和第三方服务接入形成了较完整的支撑。

从小组协作角度看，本阶段的重点不再是单个模块的快速开发，而是让移动端、管理端、后端接口、数据库结构和项目文档保持一致，保证系统能够被完整演示、完整验证和清楚说明。

## 四、遇到的问题以及解决思路

### 1. 真实接入能力对外部配置依赖较强

**具体表现：**

- 微信登录依赖有效的 `AppID`、`AppSecret` 和小程序后台配置；
- 腾讯地图依赖 WebService Key 及地点搜索、逆地址解析权限；
- 如果环境变量或第三方后台配置不完整，容易出现本地代码正常但联调失败的情况。

**解决思路：**

- 将微信和腾讯地图相关配置统一改为环境变量读取，避免硬编码敏感信息；
- 在验证手册中列出所有关键配置项和启动顺序；
- 将第三方服务失败作为单独排查方向，优先区分外部配置问题和代码实现问题。

### 2. 学校官方实名接口暂不可用

**具体表现：**

- 项目设计中需要校园实名能力，但课程环境下无法直接调用学校官方认证系统；
- 如果文档中写成“已接入学校官方接口”，会造成实现边界不清。

**解决思路：**

- 使用本地 `biz_student_roster` 学籍名单作为权威数据源模拟，实现精确匹配实名校验；
- 在文档中明确说明该方案属于“模拟但可替换”的实现；
- 保持实名接口和业务流程独立，后续如有学校官方接口，可以替换数据源而不影响主流程。

### 3. 功能增加后前后端字段和状态口径容易不一致

**具体表现：**

- 动态分类、地图选点、收藏评论、订单评价和推荐等功能涉及多个端；
- 字段命名、状态值、接口路径和页面展示一旦不统一，就会影响联调和验收；
- 文档更新滞后时，容易出现“材料写法”和“实际系统”不一致。

**解决思路：**

- 以当前源码和真实接口为准，持续更新说明文档和验证手册；
- 对关键字段保持统一命名，例如实名状态、商品状态、面交点字段、评价状态等；
- 通过完整验证清单串联用户端、管理端和后端接口，避免只验证单个功能点。

### 4. 业务能力扩展后测试和回归压力增加

**具体表现：**

- 一个功能调整可能同时影响用户端页面、管理端展示、后端接口和数据库字段；
- 订单、聊天、评价、推荐等模块之间存在数据关联，缺少回归容易引入隐蔽问题；
- 临近验收时，仅靠手动随意点击难以保证系统稳定。

**解决思路：**

- 后端补充单元测试，覆盖微信登录、实名校验、分类、地图、收藏、评论、评价和推荐等模块；
- 整理完整验证手册，按主链路逐项验证；
- 要求后续演示前保留测试输出、关键截图和日志证据，提高验收材料可信度。
